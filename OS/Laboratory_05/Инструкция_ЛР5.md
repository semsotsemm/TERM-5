## 0. Что подготовлено и что ещё требуется

В `Lab05-kit.zip` находятся `native` с четырьмя C++-программами и сборкой Windows/Linux, `simulation` с четырьмя моделями, тестами и контрольными результатами. Для Windows уже собраны x64 EXE в `native/bin`. Их можно запускать в Windows VM без установки Visual Studio. Linux-программы нужно собрать в Ubuntu.

Натурные измерения и скриншоты выполняете вы. Числа PID/TID, фактические времена и DELTA заранее неизвестны. Модельные таблицы в отчёте заполнены результатами проверенной реализации; повторите команды, чтобы получить свои снимки.

Обязательный режим — 1 000 000 итераций и задержка 200 мс каждые 1000 итераций. Один запуск занимает не менее примерно 200 секунд; при нагрузке дольше. Нулевой DELTA допустим. Не уменьшайте задержку для основной серии и не подменяйте результаты короткой проверки.

### Скриншот 1.1 — конфигурация Windows

Выполните:


Сделайте один снимок. Должны быть видны версия Windows, разрядность, модель CPU и число логических процессоров. Вставьте его на место 1.1.

### Получить маски и проверить Lab-05a — скриншот 2.1

```powershell
Clear-Host
.\Lab-05a.exe

$oneMask = $allMask -band (-$allMask)
"AllMask=$allMask OneMask=$oneMask"
```

На снимке 2.1 должны быть PID, TID, CLASS, CLASS_CODE, THREAD_REL, BASE, обе двоичные маски, CPU_COUNT, CPU и выбранные маски. Не подставляйте 255 или 1 без проверки. При 8 разрешённых CPU 0–7 полная маска обычно 255; при другом наборе она отличается.

Числовые классы процесса: 32 — Normal; 16384 — Below Normal; 128 — High. Относительные уровни потока: −2 — Lowest; 0 — Normal; 2 — Highest.

### Рабочая нагрузка — скриншот 2.2

```powershell

```

Дождитесь FINISHED. Не прерывайте Ctrl+C. Сделайте снимок 2.2: последние ITER, PID, TID, CLASS, THREAD_REL, BASE, CPU и строка FINISHED с WALL_SECONDS/CLOCK_SECONDS. Несколько десятков или сотен секунд для CLOCK_SECONDS в Windows ожидаемы, поскольку Microsoft CRT измеряет календарное время.

## 3. Windows VM — Process Explorer

Откройте Sysinternals Process Explorer (`procexp64.exe`) в VM. Предпочтительно используйте уже работавшую в этой VM версию из ЛР4. Официальная страница: https://learn.microsoft.com/en-us/sysinternals/downloads/process-explorer . Для Windows 10 не обновляйте её вслепую: текущая официальная страница новой версии указывает Windows 11 и выше. Если совместимой копии нет, используйте рекомендованную преподавателем версию либо VM Windows 11. Запустите с правами администратора при отказе в просмотре сведений.

Включите отображение PID и Base Priority через View → Select Columns; названия разделов могут немного отличаться между версиями. Для процессов ищите PID, напечатанные родителем. Для потоков откройте свойства Lab-05c → Threads и сопоставьте TID со строками программы; если доступна колонка Base Priority, покажите её. Поле текущего Priority может быть динамическим — не подменяйте им BASE.

Маску при необходимости проверьте через меню процесса Set Affinity, **не изменяя галочки**. Не задавайте Realtime и не меняйте приоритеты вручную: параметры устанавливает программа.

В Lab-05b появятся две отдельные дочерние консоли. До конца опыта их не закрывайте. После FINISHED дочернее окно ждёт Enter. Не запускайте Windows EXE в Ubuntu. Для Linux используйте `native/bin/Lab-05a` и другие файлы без `.exe`, полученные сборкой. Не берите результаты коротких тестов Docker вместо снимков VM.

### Скриншот 1.2 — конфигурация Linux

```bash
clear
cat /etc/os-release
uname -r
lscpu | grep -E 'Model name|CPU\(s\)|Thread|Core|Socket'
python3 -c 'import os; print("Allowed CPU IDs:", sorted(os.sched_getaffinity(0)))'
```

На снимке 1.2: Ubuntu, ядро, CPU и разрешённые CPU ID. При русской локали строки lscpu могут иметь другие имена; тогда выполните `LC_ALL=C lscpu` и найдите соответствующие поля.

### Скриншот 3.1 — информация Lab-05a

```bash
clear
./native/bin/Lab-05a
all_mask=$(python3 -c 'import os; print(sum(1 << c for c in os.sched_getaffinity(0)))')
one_mask=$(python3 -c 'import os; print(1 << min(os.sched_getaffinity(0)))')
printf 'AllMask=%s OneMask=%s\n' "$all_mask" "$one_mask"
```

Вставьте снимок 3.1 с PID/TID, NICE, CPU, PROCESS_MASK_BIN, CPU_COUNT, POLICY, SCHED_PRIORITY и масками. Номера CPU выше 63 данная реализация не поддерживает; в учебной VM используйте не более 64 vCPU с ID 0–63.

### Скриншот 3.2 — рабочая нагрузка

```bash
clear
./native/bin/Lab-05x 1000000 200
```

Дождитесь FINISHED. На снимке 3.2 должны быть последние итерации, NICE/CPU, WALL_SECONDS и CLOCK_SECONDS. В Linux CPU-время может быть малым, несмотря на календарные 200 секунд; это не ошибка таймера.

### Права для nice = −20

Перед запуском фоновых опытов выполните:

```bash

```

Пароль вводится до запуска фонового процесса. `sudo` нужен для разрешения отрицательного nice, а не для изменения политики на real-time. В течение опыта не повышайте приоритет посторонних процессов. Если видите ERROR или Permission denied, не используйте этот запуск в отчёте — сначала устраните отказ в правах.


## 7. Ubuntu VM — два процесса


### Вариант 1 — все CPU, nice 0 / 0

В том же терминале и каталоге `~/OS-Lab05` выполните команды по одной:

```bash
sudo -v
sudo ./native/bin/Lab-05b "$all_mask" 0 0 1000000 200 > linux-b1.log 2>&1 &
launcher_pid=$!
sleep 1
head -n 5 linux-b1.log
lab_pid=$(sed -n 's/^PARENT_PID=\([0-9]*\).*/\1/p' linux-b1.log | head -n 1)
printf 'Lab PID=%s\n' "$lab_pid"
```

`launcher_pid` может принадлежать оболочке sudo, поэтому для /proc используется PID из строки PARENT_PID. Не подставляйте номера из другого запуска.


Пока оба ребёнка работают, выполните:

```bash
p1=$(sed -n 's/^CHILD1 PID=\([0-9]*\).*/\1/p' linux-b1.log | head -n 1)
p2=$(sed -n 's/^CHILD2 PID=\([0-9]*\).*/\1/p' linux-b1.log | head -n 1)
ps -p "$lab_pid,$p1,$p2" -o pid,ppid,cls,rtprio,pri,ni,psr,stat,comm
grep -E '^(Name|Pid|Tgid|Cpus_allowed|Cpus_allowed_list):' "/proc/$p1/status" "/proc/$p2/status"
awk '{print FILENAME, "priority=" $18, "nice=" $19}' "/proc/$p1/stat" "/proc/$p2/stat"
```

Сделайте снимок **3.3**: два дочерних PID, NI 0 и 0, поля /proc с разрешёнными CPU и числовыми приоритетами. В этой команде awk имя процесса Lab-05x не содержит пробелов; для произвольных имён разбор /proc/stat требует учёта поля comm.


Для получения результата дождитесь появления зарегистрированного снимка:

```bash
while ! grep -q '^FIRST_FINISH' linux-b1.log; do if grep -q '^ERROR:' linux-b1.log; then tail -n 10 linux-b1.log; break; fi; sleep 1; done
head -n 1 linux-b1.log
grep -A 1 '^FIRST_FINISH' linux-b1.log
```

Сделайте снимок **3.4**: видны параметры запуска, SLOT победителя, PID/TID обоих исполнителей, ITER1, ITER2 и DELTA. Затем дождитесь полного окончания:

```bash
wait "$launcher_pid"
echo "ExitCode=$?"
grep '^FINISHED' linux-b1.log
```

## 9. Как написать разбор натурных результатов без выдуманных выводов

После каждого снимка замените жёлтый абзац фактическим текстом, например:

«Первым завершился исполнитель с PID … и TID …. При этом ITER1 = …, ITER2 = …, разность составила … итераций. Фактические приоритеты подтверждены … .»

Далее добавьте объяснение, которое соответствует снимку:

- При всех CPU исполнители могут обслуживаться параллельно, поэтому различие приоритетов не обязано давать большой разрыв.
- На одном CPU приоритет влияет на выбор только среди готовых исполнителей. Во время Sleep/usleep CPU свободен для другого.
- При DELTA = 0 прямо напишите, что разности по счётчикам не выявлено. Не пишите «High значительно быстрее», если это не следует из данных.
- Счётчик обновляется на каждой итерации до очередного ожидания. Оба счётчика могут достичь миллиона до выхода из последней задержки.
- Изменение CPU между строками возможно при широкой маске. При маске одного CPU другое значение CPU означает несоответствие опыта.
- Повторите подозрительный опыт с теми же параметрами; не выбирайте только удобный результат. Не отключайте 200 мс и не заменяйте нагрузку CPU-тестом без отдельного обозначения.

Заполните выводы в разделах 2.5, 3.5 и заключении. Модельные выводы уже основаны на вычисленных данных. Для нового seed MQ нужно пересчитать соответствующие таблицы и абзацы, а не менять только скриншот.
